# MA217 随身 WiFi：让 AI 带你完成原机备份与外置卡改造

把本仓库链接发给**能访问本机终端、文件和 USB 的 AI 编程助手**。AI 从只读检查开始：匹配已验证型号时进入原机备份、补丁和实机验证流程；不匹配时继续只读识别、寻找提取方法和分析固件，不直接结束任务。

```text
https://github.com/chenchen1010/ma217-mifi-unlock
请按仓库的 AI 工作流帮助我使用自备 SIM 卡。不匹配时停止套用现成补丁，继续只读识别、寻找提取方法和分析固件；不要跳过备份和验证。
```

**给收到链接的 AI：先读取 [AGENTS.md](AGENTS.md) 和 [SKILL.md](SKILL.md)，从阶段 0 开始。** 主动完成能执行的步骤；只询问工具无法取得的现场信息。未明确授权刷写时，先准备可检查的包和范围清单，再确认；已有授权不重复询问。不要把用户仅发链接等同于允许立即写 Flash。

## 这个仓库能做什么

本项目从一台自有 MA217 的原机备份中，定位并修改了外置 SIM 认证、厂家自动切卡和设备双向限速控制。实机已经通过补丁回读、使用自备电信卡上网和正常重启后自动恢复外置卡的验证。

现成补丁仅验证了 **LBF1A_N10 / LBF1ANT_N10_WH_2ESIM_V001 / ASR1803** 这一组合。外壳写着 MA217、都是 ASR、管理页长得一样，都不足以证明兼容。判断依据和精确哈希见 [设备事实卡](facts/SUPPORTED_DEVICE.md)；不同型号、不同原始程序或不同 bootloader **停止套用本补丁，转入通用只读研究**。研究方法可复用，不代表已支持其他型号的提取或刷写。

当前样机保留的是修改版。过程曾因擦除长度取整损坏相邻程序，先恢复原厂备份，再刷入修正后的最终补丁；完整错误与修复过程保留在 [踩坑复盘](docs/LESSONS.md)。

## AI 按这个顺序执行

阶段规则和分支选择以 [SKILL.md](SKILL.md) 为准。下面是匹配型号的复现路径，具体命令在 [复现操作手册](docs/REPRODUCE.md)；不匹配转入 [通用只读研究方法](docs/RESEARCH_WORKFLOW.md)。不能复制命令列表后不看结果一直执行。

| 阶段 | AI 要完成的工作 | 进入下一阶段的证据 |
|---|---|---|
| 0. 环境与任务 | 检查本机工具、连接能力和会话目标，安装并验证依赖 | 能读取本地文件和目标接口；区分离线工具可用与实机可用 |
| 1. 分层识别 | 查主板/固件、正常 USB、启动口及 bootloader | 本阶段可取得的身份项匹配；不猜 COM 号、IP 或 Flash 类型 |
| 2. 原机备份 | 小范围试读、TIM、两份独立 8 MiB 回读 | 读取完整，固件/身份区/WebUI 一致，原始 OSLO 和 OBMI 哈希匹配 |
| 3. 离线生成 | 从自己的备份生成修改包、恢复包和零擦写验证包 | 补丁、解压器、完整擦除块和包哈希全部通过检查 |
| 4. 零擦写验证 | 在本机运行验证包，再独立回读 | 正常启动，原固件和身份区原样；有本机的验证报告 |
| 5. 写入与回读 | 写入已验证包，等待全部阶段完成，再独立回读 | 补丁一致，槽外固件和身份区不变，正常启动 |
| 6. 实际验收 | 一次选卡、指定 MiFi 出口联网、正常重启后再次验证 | 活动外置卡匹配、未禁用、HTTPS 成功；重启后没有再次选卡，观察窗口完整 |

**识别是逐步补齐证据的过程。** 例如 OSLO 哈希要在回读后才有；尚未读取时，可以继续已证实适用的只读步骤。已经读到不匹配值时停止现成补丁路径，保留结果并继续只读研究，不能把“不匹配”降格为“先刷试试看”。

分支失败时，AI 必须记录失败步骤、期望值与实测值、已有本地证据，并继续尚有依据的只读路线；不能仅报告“不支持，请找厂家”就结束。禁止删除断言、修改期望哈希、使用 `python -O`、套别人的整机 dump、整片擦除或盲目重刷。已经写入而回读异常时，优先进入 [原机恢复流程](docs/RECOVERY.md)。

## 其他型号如何继续

AI 按通用研究分支建立设备档案，核对正常运行和启动阶段的接口，分别检查公开原厂固件、正常 OTA、运行期读取和启动回读的依据。对可用路线先做有界小读，再验证备份；取得镜像后离线检查布局、压缩、架构和限制逻辑。某条路线失败只关闭这一条，不把缺少诊断库或没有 OTA 更新当成所有路线的前提。

新型号没有可执行证据时，继续源码、协议和镜像分析；确需用户提供设备连接或物理操作时，说明具体缺项。通用研究不自动授权移植补丁、执行陌生 loader 或尝试刷写，也不保证每台设备都能提取成功。方法、研究记录模板及进入新型号写入前的证据要求见 [通用只读研究方法](docs/RESEARCH_WORKFLOW.md)。

## REA 在这次做了什么

REA 6.8.0 实际解析过管理页 `base.js`，也识别过 `FDIUtil.exe` 的 PE 格式；原始 ASR 诊断流则返回不支持格式。它没有直接提取本机固件，也没有完成全固件反编译。后续关键链路是自编启动口回读、Python 解析/解压、Capstone 指令分析和 Unicorn 验证，最后由实机回读与联网验收确认。

REA 是可选分析工具，不是本仓库复现路径的必需依赖或通用解锁器。具体调用、结果和证据边界见 [REA 实际作用事实卡](facts/REA_USAGE.md)。

## 哪些环境可以开始

| 使用环境 | 支持范围 |
|---|---|
| Windows x64 + 本地 AI 终端 | 本次实机验证的环境；Python 3.11，普通接口与启动 WinUSB 驱动分开检查 |
| macOS / Linux + 本地 AI | 源码阅读、公开资料检索、文件校验、离线分析/构建；可依系统工具做只读设备枚举，本仓库未验证对应 USB 回读/刷写实现 |
| 只能网页聊天的 AI | 可以解释仓库和检查用户提供的材料，无法代替本机 USB 操作；不得声称已备份或已刷入 |

安装成功、离线测试通过、实际设备改造成功，要分别报告。若用户已明确要用自备卡，沿该目标继续；若只发链接且用途不明，先完成环境检查，再询问具体目标，不要求先填长表。

## 固件下载与个人数据

[Release v1.0.0](https://github.com/chenchen1010/ma217-mifi-unlock/releases/tag/v1.0.0) 提供原始 `OSLO-original.bin`、修改版 `OSLO-unlocked.bin` 和校验清单。两份均为 **OSLO 应用程序镜像**，不是整机备份，也不能直接通过网页升级或写到 Flash 0 地址。

AI 必须用当前这台设备自己的原始备份生成刷写包和恢复包。完整备份包含本机与 SIM 身份、校准和配置，留在被忽略的 `artifacts/` 中；不上传 Issue、云盘或公开仓库。文件范围及哈希见 [固件清单](firmware/firmware-manifest.json)，分发说明见 [NOTICE](firmware/NOTICE.md)。

## 已验证什么

- 原固件恢复后回读一致；最终补丁回读匹配，槽外固件和 WebUI 不变。
- 自备电信卡正常重启后自动上网，WiFi HTTPS 通过；认证/切卡补丁有约五分钟完整观察记录。
- 现场下载：补丁前 16.68 Mbps，补丁后 25.88 Mbps，再次重启后 25.87 Mbps；不同 CDN 节点与无线条件会影响结果。
- 最终追加限速补丁的观察约 149 秒后被用户拔走中断，不能写成该轮五分钟通过。没有多天稳定性、第二台设备或其他运营商的验证。

详细证据见 [脱敏验收摘要](evidence/acceptance.json)。新用户必须完成自己的验收；作者的历史报告不能替代本机证据。
