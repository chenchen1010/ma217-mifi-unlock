# 为什么前期卡住，后来怎样拿到固件

## 前期缺的是可分析的程序输入

最初能拿到的是原网页资源、状态接口和串口运行诊断。它们能说明“何时禁卡、谁触发切卡”，但不等同于 Flash 程序，也不是可恢复镜像。

当时尝试的几个入口各有具体阻断：

| 路线 | 实际结果 | 能推出什么 |
|---|---|---|
| 搜精确版本的公开固件 | 没找到与主板和完整版本一致的镜像 | 这一搜索未取得输入，不能推出厂家没有固件或设备无法回读 |
| 设备正常 OTA 查询 | 返回没有新版本，未返回下载地址 | 这次查询未取得包，不证明没有别的提取路线 |
| 网页配置导出 | 没导出配置，HTTP 曾停止响应，重启后恢复 | 该接口不适合继续试探；配置也不是完整程序镜像 |
| CATStudio / FDI 文件读取 | 本机诊断库版本 `0x5ab2` 不匹配，数据库请求没有返回所需库 | 依赖这个库的诊断读取路线受阻，不等于启动回读也依赖它 |
| 原始诊断流交给 REA | 返回不支持该二进制格式 | 需要按实际帧格式解析，不能把日志当作已提取固件 |

因此，前期说“还没有能安全修改的固件输入”有真实依据；但把寻找完整厂家包、匹配诊断数据库当成过强的前提，推进启动口这条独立路线不够早，是这次方法上的不足。持续重复选卡、改配置，无法代替取得控制程序本体。

## 突破发生在启动阶段

正常运行时看到的接口是 RNDIS、AT 和 Diag。后来在一次正常重启中连续记录 USB 枚举，于 2026-10-29 06:30 观察到 `WUKONG / 2ECC:3001`，只存在约 1.87 秒，然后恢复普通接口。

这证明有一个独立的早期下载口。对应 WinUSB 驱动安装后，电脑可以直接与启动加载器通信。它与运行中 FDI/诊断文件系统不是同一个入口，因而不需要先拿到那份诊断命令数据库。

出现下载口还不等于已经能读取 Flash。后面继续解决了三个具体问题：

1. **握手长度。** 实际 Preamble 回显为 4 字节；最初把主机库允许读取的上限 38 当成必需返回长度，误判了会话。核对主机与设备侧协议后修正。
2. **状态机。** GetVersion 会选择下载分支。Flash Upload 必须在新启动会话中走 Preamble、ProtocolVersion、Parameters、UploadHeader；不能接在旧的版本查询会话后面。
3. **Flash 类型。** 旧主机头文件中的普通 SPI 编号 10 被本机拒绝。检查新版官方 SWDownloader 的更新记录和 PE 名称映射后，确认 ASR1803 QSPI 编号是 27；改成有依据的参数后才读出真实数据。

读取不是一次赌整片：先 256 字节，再 TIM，再固件覆盖范围和 8 MiB 回读，做独立一致性比较。最终取得了程序分析和限定范围恢复所需的原始数据，同时仍保留“物理总容量未独立确认”的边界。

## 取得数据以后，怎样逆向

先按 TIM 定位原镜像，拆出 OBMI、OSLO 等区域；OSLO 是分段 LZMA，不能把压缩字节直接当成可执行指令。解压后建立运行地址映射，再定位认证任务、云端回调和流控函数。

本次关键分析与验证实际使用 Python、Capstone 和 Unicorn：反汇编 ARM/Thumb、追踪调用和数据，再执行本机 OBMI 的原始解压与擦除包装函数。目标是对已识别的最小控制路径形成可验证结论，不要求先获得整套厂商源码或把所有程序反编译成伪 C。

IDA 可以参与对这些解压后代码的分析，但它不能代替 USB 提取，也不能仅凭一个裸镜像自动知道完整布局。Hex-Rays 的 [Binary file loader 说明](https://hex-rays.com/blog/igors-tip-of-the-week-41-binary-file-loader) 明确说明，裸二进制需要正确的处理器选择及加载地址。对于本例，已有地址映射会使后续 IDA 分析更有用。

所以不能把本次结果描述为“后来终于让 IDA 自动完整反编译成功”。实际成果是原机提取、布局/解压、关键分支分析、最小补丁，以及最后的实机验证；没有交付一个声称覆盖全固件的 IDA 反编译工程。

## 思路上真正改变的地方

- 把“提取数据”和“分析程序”分开。先证明怎样取得真实字节，分析工具才能发挥作用。
- 把网页、OTA、运行期诊断、启动下载口当成不同路径。某条路线的缺件，不自动变成所有路线的前置条件。
- 把不确定性拆成可测的小问题：端口是否出现、驱动能否打开、握手是否正确、类型编号是否正确、小范围内容是否可信。
- 用最小可解释改动解决目标，再验证真实加载器和 Flash 行为。既不等全程序反编译完才行动，也不因改动小就忽略备份和擦除边界。

最后一条也包括教训：这次最严重的启动故障来自**擦除驱动的长度取整**，并不是指令补丁本身。原先模拟截获层次过高，漏掉真实 wrapper；后来执行实际包装函数、按完整块恢复并回读，才消除了这个错误。参见 [擦除事故复盘](LESSONS.md)。
