# 成功路径与踩坑复盘

关于前期为何取不到固件、为何诊断数据库不是所有路线的前提，以及 IDA 在流程中的位置，见 [提取突破复盘](EXTRACTION_BREAKTHROUGH.md)。AI 执行约束已沉淀到 [SKILL.md](../SKILL.md)。

## 真正走通的路径

1. **认硬件和原系统**：从标签、PCB、原网页、USB 枚举和 AT 信息确定 LBF1A_N10 / ASR1803；外壳 MA217 和管理页相似都不足以认定固件兼容。
2. **先证明原厂逻辑在干什么**：插入自己的电信卡，原网页能选中并短暂上网；诊断把认证失败 → ban 与云端动作 → `USIM → eSIM1` 串起来。避免把电信频段、SIM 插反或 APN 问题和厂家控制混为一谈。
3. **找到早期启动口**：正常系统只有 RNDIS、AT、Diag；正常重启时短暂出现 `2ECC:3001`。给这个接口安装匹配的 WinUSB 驱动后，才能直接跑 WTPTP。
4. **小读、独立读、再备份**：先 256 字节，再 TIM，再 0x540000 固件范围和 8 MiB 读取；不同回读的固件一致后才分析与修改。无需先找到网上的同款固件或完整诊断数据库。
5. **还原原机布局**：TIM 定位镜像；OSLO 中分段 LZMA；解压 AP 后定位 SIMAUTH、MAINSYN 和限速初始化。最终只改 6 字节，不另造整套系统。
6. **验证真实加载 / 擦除行为**：用本机 OBMI 在 Unicorn 中执行解压和 FBF 处理，Flash 硬件层才做模拟；并以实机回读证明包确实落到预期范围。
7. **以实际使用验收**：活动卡身份、强制指定 MiFi 出口的 HTTPS、正常重启后无需重新选卡。设备运行时间的连续性用于识别真实重启，人为拔线另行记录。

## 最大的坑：请求擦除长度不等于实际擦除长度

AP 压缩槽位于 Flash `0x277000..0x309000`，长度 `0x92000`。初版包按这个范围请求擦写。

虽然底层 `spi_nor_erase` 支持 4 KiB 扇区，但其上层 QSPI wrapper `0x07811994` 会先将长度向上取整到擦除块倍数：本次 `0x92000` 变成 `0xa0000`，起点仍然是 `0x277000`。结果尾部额外 `0x309000..0x317000`、共 56 KiB 被擦成 FF，破坏下一压缩段。表现为灯同时亮、无法正常启动。

**这是本次实现中的判断错误。** 最初模拟直接截获 EraseFlash 入口，等于模拟了“希望它做什么”，漏掉实际 wrapper 取整。

修复办法是先回读确认损坏范围，然后使用原机备份恢复完整块：`0x260000..0x320000`，长度 `0xc0000`。这个范围的起点和长度都对齐 128 KiB，载荷包含补丁槽两侧的原始边界数据。恢复后固件逐字节匹配原始备份并正常启动，再写同样边界的正确补丁。

新的模拟执行原 EraseFlash、wrapper 取整、大小扇区选择，仅模拟实际 QSPI 事务，覆盖 64 KiB / 128 KiB 两种块大小。旧未对齐 apply / rollback 包不公开，也没有放进公开工具的可执行模式。

## 其他会让人绕远路的坑

| 现象或误判 | 实际原因 / 处理 |
|---|---|
| 把“有 USB 口”当成电脑必然有调试端口 | 电池、开机、线材、普通驱动和早期下载驱动分别检查；必须看实际枚举 |
| 驱动显示 1802S，就认为平台是 1802S | INF 显示名是工具包标签，须与本机 bootloader / SDK / 程序证据交叉确认 |
| 把握手读取上限 38 当成必需长度 | Preamble 真实回显只有 4 字节；应按协议实际返回判断 |
| 先 GetVersion 再直接回读 | 本机它选择下载分支；Flash Upload 要从新启动会话开始，不能混用状态 |
| 套用旧 SDK 的 SPI subtype=10 | 本机返回 UnsupportedFlashError；官方新 SWDownloader 映射确认 ASR1803 QSPI=27 |
| 16 MiB 通知证明已备份整片 | 实读两半 8 MiB 完全相同，可能地址回绕；容量仍未独立证实 |
| 改 APN / 网页选 USIM 就算解锁 | 本机稍后仍被认证任务禁用，或被云端同步切回内置卡；只解决当前选择不解决重启 |
| 其他 ASR 设备 AT 命令 / 配置导出可以照抄 | 本机多个 AT 查询 ERROR，试探配置导出曾使 HTTP 失去响应；不继续枚举未知写命令 |
| 安装 REA 就能得到固件 | REA 是分析工具，仍需本机输入、架构和协议证据；本次关键是 WTPTP 回读和 ARM 分析 |
| Python 一次 `lzma.decompress` 等同设备解压 | 固定槽带填充，可能被 Python 当成后续流；单流解码检查长度，另用原机 ARM 解码器验证 |
| Python 默认编码读取 JSON | Windows 默认编码可能误解 UTF-8 中文错误；显式 UTF-8，保留原始错误 |
| 传输完成就立刻重启 / 拔线 | FBFD 后仍有平台 Busy / Ready、验证和写入；必须等全部阶段完成 |
| 一次大包传输中断就继续盲发 | 初版大恢复包中断，原因未证实；后精简仅供验证的镜像载荷，恢复数据逐字节不变，重新验证后成功 |
| 得到重启 HTTP 200 就认为已经重启 | 可能还读到旧 uptime；必须观测运行时间下降和正常身份恢复 |
| 电脑 HTTP 成功就是 MiFi 上网 | 网线、代理或同地址路由器可能被用到；绑定源地址和网络接口，核对设备流量增长 |
| 沿用旧 WLAN IP | DHCP 实际从 `.200` 变成 `.199`，旧地址绑定失败不等于设备禁卡 |
| WinError 10049 就认定补丁导致重启 | 最后一轮是用户拔走设备；须核对 PnP、WLAN、uptime 和人为操作 |

## 限速分析应怎样表述

`hcsi.limit_speed` 初始化两向流控；原值非零时设置两向使能，调用链没有按内外 SIM 分支。补丁将一条 CBNZ 改为 `movs r0,#0`，让原函数正常清除两个方向的使能，而不是直接跳过函数、留下旧状态。

执行原函数 / setter 的模拟覆盖配置值 0、20000、50000，修改后两向使能均为 0。真实下载从 16.68 到约 25.88 Mbps，重启后约 25.87 Mbps。这支持补丁在本机工作；CDN 节点和蜂窝网络会变化，不能据此保证固定提升比例，更不能把套餐限速也算成已去除。

## 结果不夸大

认证 / 自动切卡补丁的重启后五分钟观察完成。最终追加限速补丁的回读、正常重启、USB 和 WiFi 上网、重启后测速完成；最后五分钟观察在约 149 秒后因用户拔走而中断。没有观察到的多天稳定性、其他运营商和其他固件版本仍属于未验证。
