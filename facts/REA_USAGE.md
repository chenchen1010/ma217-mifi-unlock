# REA 在本次研究中的实际作用

这是本次 MA217 实验的历史事实卡，说明实际调用与结果，不是对 REA 最新版本能力的完整评测，也不是所有输入均可处理的承诺。项目入口：[morluto/rea](https://github.com/morluto/rea)。

## 实际执行记录

使用官方 npm 包 REA **6.8.0**，运行在隔离的 Node **24.22.1** 环境，没有替换系统 Node。证据来自本次本地排查记录和分析输出；这里仅发布摘要，原始设备资源/日志留在本地，不随仓库发布。

| 输入与调用 | 实际结果 | 可以说明什么 | 不能说明什么 |
|---|---|---|---|
| 从设备取得的 `base.js`；`analyze-javascript-application` | 解析 1 个 JavaScript 文件，访问 38,037 个 AST 节点，解析失败 0 | 完成了管理页脚本的静态解析，为检查前端与接口代码提供材料 | 没有执行设备脚本；不证明接口可调用、固件已提取或限制已解除 |
| 官方工具包里的 `FDIUtil.exe`；`inspect-artifact` | 成功识别 PE 容器 | 确认该输入属于可执行程序容器，作为工具静态检查的一部分 | 不等于完整逆向其协议，也不等于本机具备可用 FDI 命令数据库 |
| 原始 ASR 诊断流；`inspect-artifact` | 返回 `unsupported binary format` | 该次调用没有处理这种日志格式 | 不能推出日志没有信息、设备不能提取或 REA 所有版本都不支持 |

JavaScript 原始输出保存在作者本地的 `artifacts/rea-base-analysis.json`，它不是仓库下载附件。输入 `base.js` 的 SHA256 为 `b25da2dd02b106d44ef03faae5bbb2e0be58d2d395169ef8a5cedfef31b11a80`；该哈希只标识这次分析输入，不能作为其他设备兼容凭据。

原始诊断流随后使用本地 Python 脚本按帧解析。登录、状态接口与联网行为另由实机请求核对；没有把 AST 节点数或 PE 格式识别当作完成解锁的证据。

## 真正完成后续各环节的工具

| 环节 | 本次实际方式 |
|---|---|
| 取得原始程序 | 发现启动阶段 WUKONG 接口，核对协议并修正主机回读脚本，经 WTPTP 从本机读取 |
| 解释固件布局 | Python 解析 TIM，定位 OBMI/OSLO 等区域，处理分段 LZMA 并建立地址映射 |
| 定位最小修改 | Capstone 分析 ARM/Thumb 指令及调用路径，结合实际诊断行为 |
| 验证解压与擦除 | Unicorn 执行原机解压代码和实际擦除 wrapper；修正早期模拟遗漏取整的问题 |
| 确认修改成功 | 独立回读、正常启动、活动外置卡、指定 MiFi 接口联网和重启验证 |

提取经过和思路变化见 [提取突破复盘](../docs/EXTRACTION_BREAKTHROUGH.md)，历史验收范围见 [验收摘要](../evidence/acceptance.json)。最终结果不是由 REA 一键提取或解锁，也没有交付声称完整覆盖该固件的 IDA 反编译工程。

## 后续 AI 应怎样选用

REA 是可选辅助分析工具，**不是当前仓库复现流程的必要依赖**。收到其他型号时先确认输入是什么、要证明什么，再选择工具；不要先强制安装 REA，再等待它自动取得固件。

如需再次使用，核对所装版本的文档、可用命令及后端依赖，保存调用、输入哈希、输出和错误；本卡中的历史命令名称不代表当前版本接口保持不变。失败后按输入类型继续选择脚本解析、反汇编或协议研究，不把某个工具失败当成结束任务的理由。不要将含身份或凭据的原始镜像/日志上传给外部分析服务。
